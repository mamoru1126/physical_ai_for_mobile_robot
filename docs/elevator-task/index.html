画像と言語の指示で、移動ロボットをエレベーターに乗り降りさせる

「扉が開いたら中に入って」「中に入ったら180度旋回して」「再び扉が開いたら出て」。この3つを文字で指示し、カメラとオドメトリだけで実行するためのソフトウェア構成を検討した。2026年11月10日時点の資料で、対象は正常系のみ。実装はこれから行う。

結論

  1. VLM を使う。VLA は今回は使わない。VLM の仕事は「指示を手順に分ける」「扉が開いたかを答える」「進む先を画像の上で指差す」の3つに絞る。車輪を動かすのは、オドメトリで閉ループ制御する小さなスキル（旋回・直進・点への移動）に任せる。
  2. このタスクの難しさは「どう動くか」ではなく「いつ動くか」にある。動きは直進と旋回だけで、オドメトリ制御の方が正確にできる。一方、「扉が開いた」には画像の意味の理解が要り、「再び」は過去を覚えていないと判定できない。前者は VLM が追加学習なしで答えられ、後者は状態をモデルの外に持てば済む。
  3. エレベーター専用のコードは書かない。扉・かご・手順の知識は、言語指示と VLM から来る。コードに置くのは汎用のスキルと「条件が成り立つまで待つ」仕組みだけにする。
  4. VLM はロボットの上で動かす。かごの中では通信が不安定になりうるので、外部の API に頼らない。Jetson AGX Orin では 2B〜8B 級の VLM が1回あたり 0.1〜1 秒ほどで応答する見込みがある（NVIDIA の公表値からの概算。実機で要実測）。
  5. 最初の作業は机上評価。対象エレベーターの画像を撮り、扉の判定と指差しの精度、応答時間を測ってからロボットを動かす。大きなリスクは2つで、「扉が開いている間に通過を始められるか」と「距離センサがなく衝突を避けられないこと」。

1要求と前提

要求の整理

要求設計での受け止め
画像と言語指示でタスクを実行する言語から手順を作り、画像で「いつ」と「どこへ」を決める
移動ロボット向け出力は並進と旋回の速度指令。差動二輪を想定する
エレベーターの乗り降り（3つの指示）「条件が成り立ったら動作する」という手順の列として扱う
正常系のみ。指定階以外では止まらない階数は読まない。乗った後の最初の「閉→開」を到着とみなす
センサはカメラとオドメトリだけ距離はカメラの幾何（床面への投影）とオドメトリから作る。障害物までの距離は測れない
指示はキーボードか Web UI から文字列でWeb UI を主にし、コマンドラインからも同じ指示文を渡せるようにする
VLM か VLA を使うVLM を使う（3章）

用語: VLM は画像と文章を入れると文章を返すモデル、VLA は画像と文章を入れるとロボットの行動を返すモデル。かごはエレベーターの箱、乗場は各階の扉の前を指す。

対象にする正常系

  1. ロボットは乗場で、扉の正面およそ1 m の位置に、扉を向いて止まっている。
  2. 人が Web UI に3つの指示を入力し、開始する。
  3. 扉が開く。ロボットはかごに入り、180°旋回して扉の方を向く。
  4. 扉が閉まり、かごが目的の階へ動く。途中の階には止まらない。
  5. 扉が開く。ロボットは乗場へ出て止まる。

エレベーターを呼ぶ操作と行先階の登録は、人か設備の側で行う。かごの中は無人で、障害物はないものとする。扉の前までの移動、ボタンの操作、階数の確認、他の乗客への対応は対象外とした。

置いた仮定

  • ロボットは差動二輪で、その場で旋回できる。
  • カメラは前向きの単眼カメラ1台で、床が写る向きに付いている。画像は 10 Hz 程度で得られる。
  • オドメトリは車輪の回転から求めた移動量と向き。
  • 計算機はロボットに載せた Jetson AGX Orin クラス（JetPack 6 系）。走行中は外部ネットワークに出ない。
  • ミドルウェアは ROS 2。
  • 数値例では、かごを 13 人乗りの規格寸法（幅 160 cm、奥行き 135 cm、出入口の幅 90 cm）[17]として計算した。

仮定が違えば構成の一部が変わる。確かめたい点は10章にまとめた。

2このタスクは何が難しいか

指示を「いつ」と「何を」に分ける

指示いつ何を
扉が開いたら中に入って扉が開いたと見えたときかごの中の目標点まで進む
中に入ったら180度旋回して前の動作が終わったときその場で180°回る
再び扉が開いたら出て扉が一度閉じ、もう一度開いたとき扉の外の目標点まで進む

「何を」は直進と旋回しかない。難しさは「いつ」の列と、それを支える周辺に集まっている。

5つの難所

  1. 「いつ」は画像の意味の理解である。扉の見え方は機種、材質、照明で変わる。判定の規則を手で書くと、対象ごとに作り直しになる。事前学習済みの VLM に「この扉は開いているか」と尋ねるだけで開閉を認識する方法は、エレベーターの扉を含む対象について、追加学習なしで実ロボットを使って試されている[4][5]。画像と文の照合だけを行う CLIP でも、エレベーターの扉の開閉を評価用の画像の 95〜100% で正しく見分けたという小規模な報告がある[20]。
  2. 「再び」は1枚の画像では決まらない。図2の A と B では、どちらもロボットの正面に開いた扉が見える。A はまだ出発階、B は到着階で、見分けるには「その間に扉が閉じた」という履歴が要る。現在の画像だけから行動を決める方式は、ここで必ず詰まる。
  3. 「どれだけ」は幾何の問題である。180°はオドメトリで測れる。どこまで進むかは、画像の上の点を床面に投影すれば距離に直せる（5.3節）。どちらにも学習は要らない。
  4. 扉には締切がある。扉が開いている時間は限られ、機種と設定で決まる。判定が遅いと乗り損ねる（6章）。
  5. 距離センサがない。人や物までの距離を測れないので、衝突の回避は保証できない。速度、距離、時間の上限で守るしかない（5.6節）。

3VLM か VLA か

3つの案

  • 案A　VLA だけで動かす。画像と指示文から速度指令までを1つのモデルで出す。
  • 案B　VLM とスキルを組み合わせる。VLM は理解（計画、判定、指差し）に専念し、動作はオドメトリ制御のスキルが担う。
  • 案C　VLM と VLA を組み合わせる。案B のうち「目標まで走る」部分を VLA に置き換える。

比較

観点案A　VLA だけ案B　VLM＋スキル案C　VLM＋VLA
扉が開くまで待つ△待機を含む教示データで学習すれば可能◎yes / no の問いに追加学習なしで答える◎案B と同じ
「再び」を扱う×現在の画像だけで決める型は、図2の A と B を区別できない◎実行器が履歴を持つ◎案B と同じ
3つの指示を順に進める×進み具合を管理する仕組みが外に要る◎計画として明示する◎案B と同じ
180°旋回する△角度を保証しにくい◎オドメトリで閉ループ制御◎旋回はスキルのまま
追加の学習データ×対象エレベーターでの教示走行と微調整が要る◎不要。ゼロショットで始められる△VLA の側に微調整が要る可能性
ロボット上の計算△大きなモデルを数 Hz で回し続ける○1〜2 Hz の判定と軽い制御×2つのモデルが常駐する
失敗の原因を追う×出力は速度だけで、理由が残らない◎計画、判定、指差しが文字で残る○上位の判断は追える
人や物を避けて走る○学習していれば見ながら避ける×発進前の確認しかできない○VLA が担う

判断

案B を採る。正常系に必要なことはすべて案B で足り、追加の学習データが要らない。弱点である「人や物を避けて走る」は正常系の範囲外で、必要になった時点で案C へ広げられる。

根拠は3つある。

  1. 案A は単体では成立しない。主流の VLA は、現在の観測と指示から次の行動を決める作りになっており、履歴に依存する課題に弱いことが繰り返し指摘されている[8][9]。ナビゲーション用の OmniVLA も、7B 級の大型モデルが観測として使うのは現在の画像で、学習に使われた言語指示は「X へ向かう」型の物体到達が中心である。著者らも、言語条件付きナビゲーションには改善の余地が残ると結んでいる[1]。過去の画像を入力に加えるナビゲーション用 VLA もあるが（NaVILA[2] など）、学習しているのは経路の指示に従う課題で、出来事を待ってから動く課題ではない。昇降の間じゅう「扉は一度閉じた」を覚えている保証もない。手順を管理し「扉が開いた」を判定する上位の仕組みは、VLA を使う場合でも結局要る。
  2. 正常系の走行に VLA の強みが効く場面がない。残る選択は、走る部分をスキルにするか（案B）VLA にするか（案C）である。正常系の走行は「1〜2 m の直進」と「その場旋回」だけで、見ながら避ける、地形に合わせるといった VLA の強みが出ない。逆に VLA を入れると、微調整のデータと常駐する計算資源が要る。
  3. 「上位は VLM、下位は別の制御器」という分担は、研究でも製品でも広く採られている。NaVILA は VLM に「75 cm 前進」のような中間レベルの行動を言葉で出させ、低位の方策がそれを実行する[2]。VAMOS は VLM に画像の上の経路を出させ、床面に投影して使う[3]。BUMBLE は、エレベーターの利用を含むスキル群を VLM が選んで呼び出す[6]。建物内ナビゲーションの研究でも、上位の判断は VLM、エレベーターの乗り降りは単純な行動プリミティブという分担が採られている[7]。そこでは扉の開きを深度のしきい値で検知しているが、本件は深度を使えないので、その役を VLM の判定に置き換える。Gemini Robotics ER 2 も、VLA やナビゲーション API を道具として呼び出す上位モデルとして提供されている[10]。VLA の研究の側でも、遅い大型モデルと速い小型モデルに分ける構成が出ている。OmniVLA を土台にした AsyncVLA は、大型の VLA を外部の計算機で動かし、ロボットの上では約 100 分の 1 の大きさの方策が最新の画像を見て行動を直す[21]。

VLM にどこまで任せるか

案B の中にも幅がある。VLM に毎回「次に何をするか」を選ばせる作り（BUMBLE[6] など）と、最初に計画を1回作らせ、実行中は yes / no と指差しだけを尋ねる作りである。本件は後者を採る。

  • 応答が速い。実行中の問いが短く、答えも数トークンで済む。扉の締切に対して有利になる（6章）。
  • 履歴をモデルの外に置ける。「再び」を、モデルの記憶ではなく実行器の状態で判定できる。
  • 動く前に確かめられる。計画の全体を人が読み、承認してから走らせられる。

VLM に任せる仕事を増やすほど、失敗の原因も VLM に寄る。BUMBLE の実験では、70 回の試行の平均成功率が 47.1% で、失敗の多くは VLM の判断の誤りだった[6]。課題の難しさが違うので数字をそのまま比べることはできないが、VLM に頼む仕事を絞る理由にはなる。想定外の状況で VLM に計画を作り直させる拡張は、正常系が通った後に考える。

VLA を後から足す道

案B の「点へ移動」スキルは、入力が目標点、出力が速度指令という単純な口を持つ。OmniVLA のように2次元の姿勢をゴールとして受け取れる VLA[1] は、この口にそのまま入る。VLM が「どこへ」を決め、VLA が「どう避けながら」を担う形になる。人がいるかごへの進入など、正常系の外へ広げるときに差し替える。

差し替えるときの制約は、ロボットの上で動くことである。AsyncVLA は通信の遅れが最大6秒あっても走れることを示したが[21]、大型モデルを外部に置く構成なので、かごの中で通信が切れる本件にはそのままでは合わない。ロボットの上だけで動かすなら、小型版の OmniVLA-edge（約 5,000 万パラメータ）が候補になる。ただし言語の理解は大型版に大きく劣ると報告されているので[1]、目標点を渡す使い方に限る。

案B で走らせたログ（画像、手順ごとの指示文、速度指令）は、そのまま言語ラベル付きの教示データになる。VLA を微調整する段階で使える。

4提案するソフトウェア構成

上の層ほど遅くて賢く、下の層ほど速くて単純にする。層の間は文字か数値でつなぎ、各層を単独で試験し、差し替えられるようにする。

ノードの一覧

ノード役割動く頻度
web_ui指示文の入力、計画の表示と承認、映像と判定の表示、停止人の操作に応じて
task_planner指示文を計画（JSON）に変える。VLM を1回呼ぶタスク開始時に1回
task_executor計画を1手順ずつ実行する。条件待ち、履歴、時間切れを管理10 Hz
vlm_perception画像と条件文から yes / no を得る。対象の記述から画像の上の点を得る判定は 1〜2 Hz、指差しは必要なとき
skill_server旋回、直進、点への移動をオドメトリで閉ループ制御する20〜50 Hz
safety_gate速度・距離・時間の上限、信号の途絶の監視、停止50 Hz
vlm_serverローカル VLM の推論サーバ（ROS の外、HTTP）呼ばれたとき

各ノードは ROS 2 のノードとして作り、スキルはアクション、判定と指差しはサービスにする。VLM は OpenAI 互換の HTTP API を持つ推論サーバ（vLLM や llama.cpp など）として別プロセスで動かす。こうしておくと、モデルを入れ替えてもノードの側は変わらない。

ロボット本体との接点は3つに絞る。カメラ画像（sensor_msgs/Image）、オドメトリ（nav_msgs/Odometry）、速度指令（geometry_msgs/Twist）である。

すべてロボットの上の計算機で動かす。制御の周期を守る必要がある skill_server と safety_gate は C++、HTTP と JSON を扱う task_planner、vlm_perception、web_ui は Python で書くのが扱いやすい。VLM の推論サーバはコンテナを分け、ROS 2 のノードとは HTTP だけでつなぐ。

名前と型流れ内容
/camera/image_rawトピック sensor_msgs/Imageカメラ → vlm_perception、web_uiカメラ画像
/camera/camera_infoトピック sensor_msgs/CameraInfoカメラ → skill_server内部パラメータ。床面への投影に使う
/odomトピック nav_msgs/Odometry台車 → skill_server、safety_gate位置、向き、速度
/cmd_vel_rawトピック geometry_msgs/Twistskill_server → safety_gate制限をかける前の速度指令
/cmd_velトピック geometry_msgs/Twistsafety_gate → 台車制限済みの速度指令
/task/planサービス（独自の型）web_ui → task_planner指示文を渡し、計画の JSON を受け取る
/task/executeアクション（独自の型）web_ui → task_executor承認済みの計画を渡す。進捗と結果が返る

トピックの名前は、台車の既存の構成に合わせて読み替える。判定と指差しの応答には、使った画像の撮影時刻を必ず含める。古い画像での判定を捨てるためと、指差しを正しい位置へ直すためである（5.3節）。

コードに書くもの、書かないもの

コードに書く（汎用）書かない（指示文と VLM に任せる）
旋回、直進、点への移動「扉」「エレベーター」「かご」という対象の知識
条件が成り立つまで待つ。一度成り立たないのを見てから、成り立つのを待つ扉が開いているかを見分ける規則

この線引きを守れば、「前の台車が動いたら2 m 進んで」のような別の指示も同じコードで扱える見込みがある。どこまで通用するかは実験で確かめる。

5各部の設計

5.1　指示文から計画へ

task_planner は、指示文、現在のカメラ画像、スキルの一覧、計画の書式を VLM に渡し、JSON の計画を受け取る。プロンプトにエレベーターの説明は入れない。

計画の1手順は「いつ（when）」「何を（do）」「時間切れ（timeout_s）」の3つで表す。「いつ」には次の3種類を用意する。

種類意味今回の指示での使いどころ
now前の手順が終わったらすぐ「中に入ったら」。前の手順の完了が、中に入ったことに当たる
when_true条件が成り立つと確定したら「扉が開いたら」
after_false_then_true一度成り立たないのを確かめた後で、成り立つと確定したら「再び扉が開いたら」

3つの指示から期待する計画は次のとおり。

{
 "steps": [
  {
   "instruction": "扉が開いたら中に入って",
   "when": {
    "type": "when_true",
    "condition": "Elevator door is fully open."
   },
   "do": {
    "skill": "go_to_visual_target",
    "target": "center of the elevator car floor"
   },
   "timeout_s": 120
  },
  {
   "instruction": "中に入ったら180度旋回して",
   "when": { "type": "now" },
   "do": {
    "skill": "rotate",
    "angle_deg": 180
   },
   "timeout_s": 20
  },
  {
   "instruction": "再び扉が開いたら出て",
   "when": {
    "type": "after_false_then_true",
    "condition": "Elevator door is fully open."
   },
   "do": {
    "skill": "go_to_visual_target",
    "target": "hallway floor 1 m past the door"
   },
   "timeout_s": 300
  }
 ]
}
  • 出力は JSON スキーマで縛る。推論サーバの構造化出力の機能を使う[18]。スキルの引数は範囲を検査する（距離は 3 m 以下、など）。
  • 条件文と対象の記述は英語で書かせる。小型の VLM は英語の方が安定すると見込むためで、机上評価で確かめる。
  • 計画は実行の前に Web UI に表示し、人が承認してから走らせる。VLM の解釈違いを、動く前に止められる。
  • 指示文に距離や角度を直接書いてもよい。「扉が開いたら 1.7 m 前進して」と書けば、計画の動作は move_straight になり、指差しを使わない。現場ごとの数値を、コードではなく指示文に置ける。

5.2　条件の判定

vlm_perception は、最新の画像1枚と条件文を VLM に渡し、yes か no だけを受け取る。

  • 答えは yes / no の2択に縛る。推論サーバの構造化出力で選択肢を固定できる[18]。出力が短いほど応答が速い（7章）。
  • 同じ答えが続けて N 回（初期値は2回）そろって、初めて確定とする。1回の誤答では発進しない。推論サーバがトークンの確率を返せるなら、yes の確率をしきい値で切る方法もある。どちらが誤りと遅れを減らせるかは、机上評価で比べる。
  • after_false_then_true は、no の確定を見た後の yes の確定で成り立つ。図2の A では発進せず、B で発進する。
  • 推論している間に届いた画像は捨て、常に最新の1枚を使う。古い画像で判定しない。
  • 画像、条件文、答え、所要時間はすべて保存する。机上評価と、後の学習データに使う。

条件文の言い回しは結果に効く。かごの中では扉までが近く、画角によっては扉の面しか写らない（水平画角 56°のカメラで扉まで 0.7 m のとき、写る幅は約 0.74 m で、扉の幅より狭い）。「扉が開いている」より「扉の向こうに廊下が見える」の方が答えやすい可能性がある。言い回しは机上評価で選び、計画を作るプロンプトの書き方の指針に反映する。

判定の遅れを減らす工夫として、画像に大きな変化があった瞬間に追加で問い合わせる方法がある。これも対象を選ばない汎用の仕組みで実現できる。

5.3　指差しから走行目標へ

「中に入って」の進む先は、VLM に画像の上で指差してもらう。対象の記述（例: かごの床の中央）に対して、VLM は画素の座標 (u, v) を返す。Qwen3-VL 系は、点や矩形を 0〜1000 の相対座標で出力できる[11]。

床の上の点であれば、カメラの高さと向きが分かっていれば、画素から距離に直せる。

カメラの内部パラメータを fx, fy, cx, cy、床からの高さを h、俯角を θ、ロボット中心からカメラまでの前後の距離を xc とすると、ロボットから見た床の点 (X, Y) は次の式で求まる。X は前方、Y は左を正とする。

a = (u − cx) / fx b = (v − cy) / fy s = h / (sin θ + b cos θ) X = xc + s (cos θ − b sin θ) Y = − s a

s の分母が正のときだけ有効で、これは画素が地平線より下にあることを意味する。得た (X, Y) をオドメトリ座標の目標点に直し、そこまで走る。目標をオドメトリ座標で持つので、近づいて目標が視野の下へ外れても走り切れる。走行中に指差しを繰り返して目標を更新すれば、近づくほど誤差が減る。画像の上の経路を床面へ投影して使う考え方は、VAMOS でも採られている[3]。

オドメトリ座標へ直すときは、指差しに使った画像を撮った時刻のロボットの位置を使う。推論の間もロボットは進むので、応答が返った時点の位置で直すと、推論時間と速度の積だけ目標が奥へずれる（0.5 秒、0.3 m/s なら 15 cm）。そのために skill_server はオドメトリの履歴を短く保持する。tf2 を使っていれば、撮影時刻を指定して変換を引ける。

誤差の目安を計算した。カメラの高さ 0.5 m、俯角 15°、焦点距離 600 画素（640×480 画素、水平画角およそ 56°、垂直画角およそ 44°に相当）で、指差しが 10 画素ずれた場合の値である。この取り付けでは、床は約 0.7 m 先から写る。

目標までの

ずれは指差しの誤差に比例する。扉の通過で効く横方向は小さい。奥行き方向は距離の2乗で増えるが、近づきながら更新すれば抑えられる。VLM の指差しが実際に何画素ずれるかは、机上評価で測る。

止まる位置の余裕も見ておく。奥行き 135 cm のかごの中央に、たとえば長さ 60 cm のロボットを止めると、前後の余裕は約 37 cm ずつになる。1.7 m 先の目標は、10 画素のずれで約 10 cm、30 画素のずれで 30 cm 前後ずれる。発進の前に1回指差すだけで止まる位置を決めるのは危うく、近づきながらの更新を前提にする。

指差しの結果は、走る前に3点を検査する。点が返っていること、点が地平線より下にあること、目標までの距離が上限（初期値 3 m）以内であること。どれかを満たさなければ、走らずに指差しをやり直す。

かごに特有の注意がある。車椅子に対応したかごでは、入口の正面の壁（奥の壁）に鏡を設け、その下端を床から 40 cm 程度にするという整備基準がある[17]。壁や扉が光沢のある金属であることも多い。VLM が鏡に映った床を指差すと、目標が奥の壁の先に置かれてしまう。指差した点が実際の床の上にあるかを VLM にもう一度尋ねる、目標までの距離に上限をかける、の2つで防ぎ、机上評価で確かめる。

必要な較正は、カメラの内部パラメータと、床からの高さ、俯角の3つで、一度測れば済む。

速度の上限は、初期値として並進 0.3 m/s、旋回 0.8 rad/s とする。この値で 180°の旋回は加減速を含めて約5秒、1.7 m の走行は約6秒かかる。

5.5　実行器

task_executor は、計画を上から順に進める小さな状態機械である。各手順は「条件待ち」「動作中」「完了」と進み、時間切れか異常で「中止」に移る。中止では停止し、Web UI に理由を表示する。

実行器が持つ状態は、現在の手順、条件の履歴（成り立たないのを見たか）、スキルの結果、開始時刻である。状態をモデルの外に置くことで、「再び」のような履歴に依存する条件を確実に扱える。

1つ前提を置いている。旋回が終わるまでの時間が、扉が閉じてから目的の階で再び開くまでの最短時間より短いことである。旋回は約5秒で終わる。戸閉、昇降、戸開には1階分でも10秒程度はかかると見込んでおり、正常系では成り立つはずだが、対象のエレベーターで実測して確かめる。

5.6　安全ゲート

skill_server の出力は、必ず safety_gate を通してから台車に渡す。

  • 速度の上限と、1回のスキルで動ける距離と時間の上限をかける。
  • カメラ画像、オドメトリ、VLM の応答のどれかが途絶えたら停止する。
  • Web UI の停止ボタンと、物理的な非常停止を受け付ける。
  • 発進の直前に「進路に人や物がないか」を VLM に確認し、問題なしと答えたときだけ発進する。

カメラとオドメトリだけでは、走行中に現れた人や物を検知して止まる保証がない。実験は低速で行い、かごの中を無人にし、非常停止を手にした人が立ち会う前提で計画する。接触を検知するバンパは要求の範囲外だが、追加を勧める。

5.7　Web UI

ロボットの上で Web サーバを動かし、同じ LAN にある PC やスマートフォンのブラウザから使う。画面には次のものを置く。

  • 指示文の入力欄
  • 生成された計画（手順ごと）と、承認のボタン
  • カメラ映像。指差した点と判定の結果を重ねて表示する
  • 現在の手順と経過時間
  • 停止ボタン
  • VLM とのやり取りのログ

キーボードだけで使う場合は、同じ指示文をコマンドラインから渡す。

時間予算

扉が全開になってから、ロボットの先端が敷居に届くまでの時間を見積もった。

要素時間
判定の確定（2 Hz で2回一致、推論 0.3〜0.9 秒）約 1〜2 秒
指差しと目標の計算約 0.5〜1 秒
敷居までの 1.0 m を 0.3 m/s で走る約 3.5 秒
合計約 5〜6.5 秒

この合計が、対象のエレベーターで扉が開いている時間より短くなければならない。参考として、米国の ADA 基準は、全開の保持を最低3秒（かごの中からの呼び）、乗場からの呼びでは到着の通知から戸閉の開始まで最低5秒と定めている[15]。これに照らすと、初期値のままの 5〜6.5 秒では間に合わないおそれが大きい。日本の対象機で実測したうえで、次の手段で縮める。

  • 待機位置を扉に近づける（敷居の手前 0.5 m 程度）。そのためには、1 m ほど先の床がカメラに写る必要がある。高さ 0.5 m に水平に付けた垂直画角 44°のカメラでは、床は約 1.25 m 先からしか写らない。俯角を 15°付ければ約 0.7 m 先から写る。足りなければ広角のものにする。
  • 判定と指差しを1回の問い合わせにまとめる（開いていれば床の点を返し、閉じていれば何も返さない）。
  • 走行速度を上げる（0.5 m/s 程度）。
  • 条件を「全開」ではなく「通れる幅まで開いた」にする。扉が開き切るまでの時間を走行に使える。条件文を変えるだけで試せるが、開く途中の扉へ向かって走ることになるので、判定が安定することを机上評価で確かめてから使う。
  • 開いたと確定した時刻を覚えておき、発進までに決めた秒数を超えたら、その回の乗車を見送る。秒数は実測した時間から決める。
  • 最初の実験では、人が「開」ボタンを押して扉を保持する。

はじめの3つを入れると、判定の確定に約 1〜2 秒、0.5 m の走行に約 1.5 秒で、合計は約 2.5〜3.5 秒まで縮む見込みである。

扉の側にも備えはある。ADA 基準は、閉まりかけた扉が人や物に遮られたら止まって開き直す装置を求めており、接触を必要としない方式で、遮られている間は少なくとも 20 秒有効であることとしている[15]。日本の機種にも、戸が閉まる間に出入口の赤外線ビームで人や物を検知するセンサを標準で備えるものがある[16]。ただしこれは最後の砦であり、設計の上では当てにしない。

JetPack 6 系と vLLM での参考値

想定している JetPack 6 系に近い条件の公表値が2つある。

  • Embedl は、Jetson 用の vLLM 0.14.0 で動かした Cosmos-Reason2-2B について、Jetson AGX Orin での測定値を公表している[22]。4 ビットに量子化した版（W4A16）は、画像1枚の入力で最初のトークンまで約 56 ミリ秒、以後は1トークンあたり約 12 ミリ秒。量子化前は約 58 ミリ秒と約 24 ミリ秒である。5 トークンの答えなら、量子化版で約 0.1 秒の計算になる。
  • 同じ量子化版を Jetson AGX Orin 64GB（JetPack 6.2.2）で動かした利用者は、1フレームあたりおよそ 0.5〜0.8 秒と報告している[23]。問いと出力の長さは書かれていない。

条件によって数倍の開きがある。対象の画像と実際の問いで測るまでは、判定1回を 0.3〜0.9 秒と見ておく（6章の時間予算はこの幅で計算した）。

同じ報告には注意点もある。Jetson AI Lab の手順は FP8 の重みを使うが[12]、AGX Orin では FP8 版の出力が崩れ、W4A16 版に替えて正常になったという[23]。モデルを載せたら、最初に短い問いで出力が正しいことを確かめる。

進め方

まず 8B 級のモデル1つ（Qwen3-VL-8B か Cosmos-Reason2-8B）で、計画、判定、指差しのすべてを試す。判定の遅れが時間予算に収まらなければ、判定だけを 2B〜4B に分ける。どれを使うかは机上評価の結果で決める。

コードを書く前の当たりは、NVIDIA の Live VLM WebUI で付けられる。カメラの映像を推論サーバへ流し、問いへの答えをブラウザに表示する道具である[12]。扉の前にカメラを置いて「Is the elevator door open?」と尋ねれば、判定の感触がその場で分かる。

ロボットが外部ネットワークに出られない場合、コンテナとモデルの重みは別の PC で取得し、持ち込む。

敷居の段差や溝で車輪が滑るオドメトリがずれる敷居は直進で越える。オドメトリは短い距離だけに使い、指差しで補正する

9進め方

段階0　机上評価（ロボットは動かさない）

  • 最初に Live VLM WebUI（7章）で、対象の扉を前にして判定の感触を見る。
  • 待機位置とかごの中の2か所から、扉の開閉をそれぞれ10回以上撮る。照明と時間帯を変える。
  • 候補のモデルと条件文の言い回しを変え、判定の遅れと誤った確定の回数を数える。
  • 床に目印を置き、指差しを床面に投影した位置と実測との差を測る。奥の壁に鏡があるかごでも試す。
  • 扉が開いている時間と、戸閉から次に開くまでの時間を測る。

合格の目安: 扉が閉じている間の誤った yes の確定が0回。全開から確定までが 1.5 秒以内。1.7 m 先の指差しで横のずれが 10 cm 以内。

段階1　最小の構成で通す

  • 判定は VLM、動作はオドメトリの直進と旋回だけにする。進む距離は設定値で与え、ロボットは扉の正面に置く。
  • 計画は 5.1節の JSON をそのまま読み込む。計画の生成は次の段階で入れる。

合格の目安: 3つの指示の通し実行が、続けて5回成功する。

段階2　提案した構成にする

  • 計画の生成と承認の画面、指差しと床面投影による目標点、ログの保存を入れる。
  • 初期位置をずらして試す（横に ±20 cm、向きに ±10°）。

合格の目安: 同じ指示文から10回続けて、5.1節と同じ構造の計画が得られる。通し実行が10回のうち9回以上成功する。扉を通るときの横のずれが 10 cm 以内。

段階3　正常系の外へ広げる

  • かごに人がいる場合の待機と中止、階数表示の読み取り。
  • 「点へ移動」スキルの VLA への差し替え、集めたログでの微調整。

10確認したいこと

  • カメラ: 画角、解像度、取り付けの高さと俯角。床が何 m 先から写るか。
  • ロボット: 幅と長さ、その場旋回ができるか、バンパの有無。
  • 計算機: Jetson AGX Orin のメモリ容量と JetPack の版、同時に動かす他の処理。
  • 対象のエレベーター: 出入口の幅、かごの奥行き、扉が開いている時間、扉の材質（鏡面、窓付きなど）。
  • 待機位置までの移動: 誰がロボットを扉の前まで運ぶか。この資料は、扉の正面に置かれた状態から始めている。
  • 実験の体制: 立会い、非常停止の手段、エレベーターを占有できる時間帯。
